# Video loss recovery

The host retains original SRTP ciphertext for NACK repair. It never rebuilds a packet with the same SRTP packet index and changed headers. The cache is private to each peer, bounded to 4096 packets / 8 MiB / 1.5 seconds, and cleared on close. Each cached packet can be retried at most three times, at least 80 ms apart. A bounded feedback queue and shared pacing budget (approximately 25% of configured video bitrate) limit repair traffic.

Feedback is parsed only after SRTCP authentication succeeds. All Generic NACK PID/BLP blocks are decoded, including 16-bit wraparound. Matching uses the local video SSRC, not the diagnostic event stream index. PLI and FIR target the appropriate video track; duplicate requests are coalesced. The encoder starts each connection with an IDR and uses on-demand refresh rather than periodic IDRs. Authenticated PLI/FIR refreshes the requested encoder at most once every two seconds; peer connection, input, audio and other displays stay active. The current FFmpeg pipe backend restarts that encoder for a refresh rather than forcing a keyframe in place. With no periodic keyframes, recovery depends on receiver feedback and the bounded NACK cache; clients with missing feedback remain a compatibility risk.

The installed SIPSorcery 10.0.16 diagnostic feedback model exposes only the first NACK block, hence the authenticated compound RTCP parser in VideoRecovery.cs. The library's receiver reorder buffer also drops certain out-of-order repairs. The local loss fixture therefore sends ordered NACKs with 15 ms delay, keeping strict complete-frame and decoder-error assertions. It simulates 0%, 1%, 3%, and 5% first-transmission loss; it is not evidence of WAN or official-client performance. Receiver buffer limitations remain relevant to our controller implementation.

Run tests/URemote.Checks with --video-recovery and the path to an FFmpeg executable. The test uses synthetic video and real DTLS/SRTP/SRTCP sessions, verifies byte-exact ciphertext repairs and full FFmpeg decode, and covers cache lifetime, retry bounds, SSRC isolation, NACK blocks, PLI and FIR parsing. Official-client validation remains necessary.

## Official Windows receiver comparison (2026-09-29)

UU Windows 4.42.0.2770 in the authorized QEMU lab received the installed host for about nine minutes without a persistent freeze. At 1920x1080/60 it reported about 57–58 rendered FPS. This is a local user-mode NAT path with a software-decoding VM, not the user's WAN/device combination.

A temporary QEMU packet relay then discarded first-transmission video packets while passing repairs unchanged. With 1% loss, 378 packets were deliberately discarded; the receiver stayed near 57 FPS. A second 60-second run introduced 3% first-transmission loss and 150 ms receive delay after a 10-second baseline: 1173 packets were discarded and the reported render rate remained near 57 FPS. Temporary redirectors and character backends were removed after each test. No packet payloads were written to disk. These bounded tests do not reproduce bandwidth starvation, arbitrary burst loss, remote relay behavior, or the user's hardware decoder.

The user's WAN freeze is still unresolved. Diagnostics now report RTT derived from authenticated receiver reports, cache misses/expiry/retry throttling, queue overflow, and actual socket send errors. A successful socket send is not proof of remote receipt. Cache misses include entries already evicted or expired; they must not all be interpreted as delayed requests. Invalid or unavailable RTT is reported as unknown, not zero. No bitrate policy change was made based solely on the VM comparison.

## Desktop quality stability (2026-09-30)

Fixed-rate, static-image encoding reproduced periodic quality collapse without a network: the old ultrafast preset, half-second IDRs and 125 ms VBV caused a roughly 15 dB PSNR dip on a color-pattern fixture. A dense text fixture exposed worse dips even with a larger VBV when half-second IDRs remained enabled. The production encoder now uses veryfast, 500 ms VBV and keyint=infinite with scenecut disabled. VBV is a rate-control budget, not an added playback queue. Zerolatency, no B frames and the existing packet pacing remain in use. Sparse/initial IDRs can still be larger and take longer to transmit; frame size and WAN responsiveness must be checked in actual use.

The production-encoder quality check feeds 720 static 1080p frames, verifies an initial IDR with no periodic IDRs, and decodes the entire output with FFmpeg. A separate dense-text 12-second fixture remains stable after its initial refinement. Synthetic moving-pattern throughput on this machine measured about 245 FPS at 1080p and 149 FPS at 1440p with two encoder threads; these are offline encoder measurements, not end-to-end remote FPS. Existing 0/1/3/5 percent loss and PLI/FIR recovery tests passed. The adaptive bitrate controller still restarts the encoder when it changes the bitrate, so occasional quality transitions during adaptation remain possible.

Run `tests/URemote.Checks --video-quality-checks <ffmpeg-path>` for the production encoder check.

## High-frame-rate support (2026-09-30)

The advertised encoding ceiling and encoder validation now accept up to 144 FPS instead of 60. The capture-request decoder honors a standard selected 30/60/90/144 tier first, falling back to the explicit FPS field when no standard tier is selected. Live requests kept the explicit field at 60 even after capability refresh while the selected tier was 144; honoring that field first masked the high-FPS selection. Client reconnection is required to refresh advertised capabilities. H264 signaling and the encoder use level 5.2 to accommodate 1080p at 144 FPS; the previous level 5.1 caused an x264 macroblock-rate warning at that mode. This is not a claim of 4K144 support or guaranteed real-time throughput at every resolution.

The production-encoder test `--video-144-checks <ffmpeg-path>` feeds 720 frames through the 144 FPS configuration and decodes all of them. The raw H264 decoder fixture must be given the configured input frame rate to avoid a false null-muxer DTS error. Profile tests cover 120, 144 and bounding requests above 144; screen capability tests cover the new advertisement. This does not verify actual display capture or official-client render rate at 144 FPS. The currently attached display was running at about 60 Hz and advertised a maximum 1080p120 mode, so it cannot supply 144 unique screen updates per second. No display mode was changed as part of the software update.

### Active-display ceiling

The host now reads `wl_output.mode` CURRENT refresh in millihertz at startup and on each new viewer session. Both capability messages and video profiles use each display's ceiling: min(rounded current Hz, 144). Missing metadata falls back to 60 FPS; supported-but-inactive display modes are not used. Thus a 144 FPS selection on a current 120 Hz display configures 120 FPS, while an explicit lower request remains lower. Multi-display and iOS single-track selection preserve per-display ceilings. A display-mode change during an existing session currently requires reconnecting to refresh the ceiling. This limits requested capture/encoder cadence; actual delivered/rendered FPS can still be lower under load or network loss.

Live Wayland validation on this machine returned 120000 mHz and a 120 FPS ceiling. Offline tests cover mixed 120/60 Hz outputs, lower requested rates, mobile switching, fractional refresh rates and capability serialization. `--display-refresh-checks` reads only display metadata, not screen contents.

## Quality menu capability limits (2026-09-30)

The host previously advertised the current monitor dimensions as its H264 codec capability. Native clients intersect encoder and decoder sizes before allowing quality tiers, so a 1080p monitor incorrectly restricted even a capable receiver to HD. The host now advertises its supported 3840x2160 H264 4:2:0 8-bit encoding size, separately from the physical monitor dimensions and refresh ceiling. This does not upscale capture or claim 4K144 throughput, hardware encoding, H265, HDR or 4:4:4 support. `--video-4k-checks <ffmpeg>` validates 60 synthetic 4K30 frames through the production encoder and decoder.

In the authorized Windows 4.42.0.2770 VM, Original was rejected with the device-performance/HD-only message before any quality request reached the host. Its connection request advertised only 1920x1080 H264 software decoder capabilities (implementation 37), explaining why increasing the host capability alone did not remove the VM's restriction. This VM cannot validate successful higher-tier selection; a receiver advertising a larger decoding size must be tested separately. Numeric controller codec capability diagnostics now make this distinction visible without logging identities or tokens.

## Quality budgets and receiver feedback (2026-09-30)

The Windows menu's HD / Ultra / Original tiers map to wire values 2 / 3 / 4 (legacy names General / HD / Bluray). Their configured rate ceilings are now 8 / 14 / 30 Mbps, with x264 CRF 23 / 18 / 14. These align the observed menu budgets; they do not claim to duplicate the proprietary encoder or every resolution/FPS-dependent recommendation of every official version. Capture remains bounded by actual screen size and refresh rate. CRF encoding is variable-rate: a static desktop need not consume the advertised budget, and Original is not lossless.

The former unconditional Windows 4 Mbps startup cap is removed. Fresh connections can immediately use the selected tier. Authenticated receiver feedback still reduces the ceiling for >=3% loss or a stalled decoder, and two healthy intervals increase it gradually up to the requested budget. Repeated manual requests do not bypass a measured congestion ceiling. This protects recovery, but congested connections may still deliver less than the selected rate.

Capture RPC field 12 now preserves the client's automatic quality target instead of always using 12 Mbps. Field 8 carries custom bitrate in bits per second; the implementation supports 1–40 Mbps, rejects larger custom requests, and retains settings across FPS-only changes. The diagnostics distinguish requested budget, effective budget and network ceiling. Local profile/protocol checks cover all tiers, automatic/custom persistence, per-display frame limits, loss protection and recovery. Official-client rendering after this policy change requires live validation.

Live VM validation after installation: Windows 4.42.0.2770 sent quality=2 for “HD 8M”; both automatic-HD and manual-HD used an 8,000,000 bps ceiling with CRF 23 and 1920x1080/60. The displayed video continued updating. Ultra/Original remain blocked by this VM's advertised software decoder size, so their revised budgets are covered by local profile tests rather than an official-client render test. Custom-rate live validation is also still pending.
